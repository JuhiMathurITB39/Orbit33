# Known Limitations (kept current; see also DECISIONS.md)

## Verified-status legend
- **VERIFIED**: implemented and exercised by tests or commands run in this environment (evidence in TEST_RESULTS.md).
- **SIMULATED**: runs, but on simulated data/assumptions.
- **NOT EXECUTED**: authored but could not be run here.
- **OUTSTANDING**: not built.

## Data
1. Real M5 data was not available (Kaggle blocked). All demand results are on **simulated M5-schema data** (SIMULATED).
2. Inventory, purchase orders, supplier performance and replenishment events are **synthetic** by design (SIMULATED).
3. Stockout labels are simulation-derived, not observed.
4. Simulated demand is generated by a known process, so forecasting accuracy here is likely **easier than on real M5**. Do not quote it as real-world accuracy.

## Stack substitutions (see DECISIONS.md)
5. No Parquet/PyArrow, FastAPI, SQLAlchemy, XGBoost, LightGBM, statsmodels, MLflow, Vite, Recharts.
6. Airflow DAGs and dbt models: authored, **NOT EXECUTED**.
7. Docker/Compose, Dockerfiles and AWS IaC: authored, **NOT EXECUTED** (no Docker daemon, no AWS access). No cloud deployment exists; there is no live demo link.
8. Frontend is **not type-checked** (`tsc` cannot resolve React types offline); it bundles with esbuild and was exercised in headless Chromium. Charts are hand-built SVG with limited interactivity (hover tooltips only on scatter points). No automated UI tests.

## Product
9. No user interviews have been conducted. `product/USER_RESEARCH.md` contains a guide and empty templates only.
10. The A/B experiment in `product/EXPERIMENT_PLAN.md` is a design; it has not been run.
11. Simulated cost savings are backtest results under stated assumptions, not realised commercial savings.

## Security (portfolio deployment)
12. API-key auth is a minimal architecture demonstration; there is no user management, rate limiting, TLS termination or audit log.

## Added during the build
13. The policy backtest uses **one demand path**; its 5 replications vary supplier randomness only, so the reported sd understates uncertainty.
14. ORBIT's design was tuned after seeing the first backtest (D-012). ORBIT optimises the same cost model the simulator evaluates; the incumbent does not. Real-world gains could be smaller or negative.
15. The ML forecast contributes little to simulated decision cost (ablation: 0.6%). Most gain vs the default incumbent is batching and retuned cover levels, at 3.7× the working capital of the default.
16. Stockout labels come from the simulator that also generates the features, so the lift over the on-hand-cover baseline (PR-AUC 0.81 vs 0.70) is probably optimistic. The supplier-late model has weak signal (PR-AUC 0.31 vs 0.29 baseline).
17. The default storage constraint is binding for CA_1 in the default plan (storage 99.8% utilised), so recommended quantities are scaled down; storage capacities are synthetic.
18. API: per-process caches (restart to refresh), no pagination on `/suppliers`, no rate limiting, minimal OpenAPI (paths only), no concurrency/load testing, auth is a single shared key.
19. Assistant: keyword intent matching, not language understanding; phrasing outside its patterns is refused. The optional LLM path was not tested against a live model.
20. dbt SQL was run as plain SQL on PostgreSQL 16, not through dbt. PostgreSQL DDL and data load were verified locally; no managed Postgres, Airflow, Docker or Terraform execution occurred.
21. Single test fold (13 weeks) per horizon; single seed.
22. Inventory snapshot "as of" is the last simulated day (2016-05-22), so "next 7 days" refers to the simulated future.
23. The real-M5 code path (`ORBIT_M5_DIR`, optional `ORBIT_STORES` / `ORBIT_ITEMS_PER_DEPT` subset) was tested only on simulator output presented as if it were real M5, including a store id the original code did not know. It has **not** been run on the real Kaggle files; real data may expose issues (e.g. pre-launch zero sales, price gaps, runtime/memory on all 30k series).
24. Windows: the build and all tests ran on Linux. A Windows-only crash (`resource` module) and a read-only SQLite path issue were fixed after a user report; no other Windows testing was done.
25. **First run on real M5 (3 stores x 56 items, user-reported) found three problems, two fixed:**
    (a) Windows crash on `import resource` - fixed. (b) Real M5's calendar is 28 days longer than its sales columns; those days were simulated as zero demand and shifted the "as of" date and backtest window - fixed (calendar truncated to days with sales; regression test added). (c) When a baseline (moving average) won model selection, no forecasts were served and the API returned 500 - fixed (baselines are now served; test added).
26. **Open: on that first real-data run ORBIT's cost mode did not beat a tuned incumbent** (user's run, which still had bug (b): ORBIT $34.2k vs tuned $20.1k vs default $32.1k; ORBIT service-95 mode $24.5k). Real M5 items are low-volume (about 0.7 units/day per series in the subset). I reproduced the pattern on simulator data thinned to similar volumes (ORBIT $29.9k vs tuned $22.5k) and traced it to the synthetic storage cap: it limits position to about 52 days of average demand, ORBIT's reorder level is set before the cap is considered, so batches shrink and it places ~60% more orders. With the storage cap removed for ORBIT only, the same run gave $18.7k (better than the tuned incumbent). So the simulated-data headline (-5.8% vs tuned) does **not** generalise to low-volume items under a tight storage cap, and the optimiser needs to choose reorder level and batch jointly when storage binds. Not yet fixed. The storage cap is itself a synthetic assumption.
